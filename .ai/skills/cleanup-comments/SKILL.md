# Cleanup Comments

Remove comments that add reading and maintenance cost without adding durable
information. Judge comments by their value, not by whether they sound AI-written.
Do not claim a comment was generated by AI unless there is direct evidence.

The audience is a future maintainer who has the current file open but does not
know the prompt, diff, review discussion, or previous implementation.

## Scope

Use the invocation argument as the scope. Pi appends it as trailing `User:` text
after the skill content; harnesses that support interpolation may expose the same
value as `$ARGUMENTS`. The frontmatter `argument-hint` is a display hint for
harnesses that support it.

- A file or directory means inspect all source comments in that path.
- `diff` means inspect comments added or changed in staged, unstaged, and
  untracked source files.
- `branch` means inspect comments added or changed since the merge base with the
  repository's default branch, including staged, unstaged, and untracked source
  files.
- `repo` or `all` means inspect the whole repository.

With no argument, inspect comments added or changed on the current branch plus
staged, unstaged, and untracked source files. If there are no changed comments,
ask for a path rather than sweeping the repository without permission.

Before editing, read the repository instructions and its comment and public API
documentation conventions. Keep unrelated worktree changes intact. List untracked
files separately with `git ls-files --others --exclude-standard`; ordinary
`git diff` commands do not include them. Skip vendored, generated, minified, lock,
snapshot, and third-party files unless the user names them explicitly.

## Decision test

Read the surrounding code before judging a comment. For each comment or coherent
comment block, ask:

1. Is it required machinery or project-required documentation?
2. Does it state an enduring fact that names, types, tests, and code cannot state
   clearly enough?
3. Would it help a maintainer who never saw the change that introduced it?
4. Is it accurate for the current code and placed near what it describes?
5. Is every sentence needed?

Preserve required machinery and comments with durable information. Delete a
comment when the answer to questions 2 and 3 is no. Trim it when only part of it
carries durable information. If a comment contradicts code, delete it only when
it is clearly obsolete and carries no current contract. Otherwise report the
conflict because the code may be wrong. If the answer is uncertain, preserve the
comment and report it instead of guessing.

Do not use keywords or comment length as automatic deletion rules. `now`, `old`,
`important`, or a long block can be valid in context. The test is informational
value.

## Delete with high confidence

- **Code narration:** translates the next statement, branch, loop, return, or
  symbol name into prose.
- **Step labels:** headings such as `Validate input` or `Return result` where the
  code already provides the same structure.
- **Change narration:** describes the edit, prompt, review, or removed
  implementation rather than the current constraint. Examples include `now uses`,
  `new approach`, `previously`, `as requested`, and defenses aimed at a reviewer.
- **Signature echo:** doc text that only repeats a function name, parameters,
  return type, or field type and is not required by the ecosystem.
- **Tutorial voice:** explains ordinary language syntax or a familiar library call
  to the expected maintainer.
- **Decoration:** banners, separators, and section prose that do not help readers
  find their way through a genuinely long file.
- **Placeholder residue:** `your code here`, generated walkthrough text, empty
  comment blocks, and abandoned scaffolding.
- **Commented-out code:** delete it when version control already preserves it and
  no current constraint depends on seeing it.
- **Unsupported filler:** claims such as `robust`, `safe`, or `handles errors`
  that add no precise contract or rationale.

A sequence of comments narrating nearly every line is strong evidence that each
comment is redundant, but still inspect each one for a hidden constraint before
deleting the block.

## Preserve

- License and copyright notices, shebangs, generated-file markers, build tags,
  editor directives, formatter controls, coverage controls, and linter or type
  suppression directives.
- Comments consumed by tools, including structured annotations and documentation
  tags. A comment can affect compilation, typing, tests, generated docs, or
  runtime behavior even when it looks like prose.
- Public API documentation required by the language, linter, or project. Keep
  useful contract details such as units, ownership, errors, side effects,
  concurrency guarantees, and compatibility behavior.
- Rationale for non-obvious choices, rejected alternatives a reader would
  reasonably consider, compatibility constraints, workarounds, and deliberate
  deviations from convention.
- Invariants, ordering requirements, security boundaries, performance limits,
  protocol details, domain rules, and failure modes that code cannot express.
- Citations to issues, incidents, specifications, RFCs, upstream bugs, or external
  documentation when they support a current decision.
- Explanations of genuinely complex regular expressions, formulas, algorithms,
  wire formats, and test scenarios.
- Actionable TODO or FIXME comments that follow project convention. Flag vague or
  stale debt comments rather than silently deleting a possibly real obligation.
- Section comments that provide useful navigation in long declarative, schema,
  configuration, or generated-adjacent files.

Do not remove docstrings or other string literals as part of a comment-only pass.
Some languages expose them at runtime. Do not mistake URLs, heredocs, templates,
regular expressions, or data containing comment delimiters for comments.

## Editing rules

Make comment-only changes. Do not change executable code, rename symbols, or
refactor control flow during this skill. If a bad comment reveals unclear code,
report the possible refactor separately.

Prefer deletion over rewriting. Rewrite only to retain a clear, known constraint
from an otherwise redundant or historical comment. Never invent a rationale.
Keep the smallest wording that preserves the useful fact, and follow the file's
existing comment style. When deleting an inline block comment between tokens,
retain separator whitespace if direct removal would join or change the tokens.

Do not create a cleanup report file unless the user asks for one.

## Verification

1. Re-read each edited hunk with surrounding code and confirm the remaining text
   is accurate.
2. Inspect the final tracked diff and each edited untracked file. For an untracked
   file, use `git diff --no-index -- /dev/null <file>` without staging it. Confirm
   this pass changed only comments, separator whitespace, and blank lines directly
   left by removal. Separate pre-existing worktree changes from this pass.
3. Run `git diff --check`. For each edited untracked file, also run
   `git diff --no-index --check /dev/null <file>` without staging it. An exit status
   of 1 is expected because the file differs from `/dev/null`; emitted whitespace
   diagnostics are failures.
4. Run a language-aware parse, compile, or syntax check when inline comments were
   removed, then run relevant non-fixing lint, type, documentation, or test tasks
   when comment directives or documentation tooling could be affected. Do not run
   an auto-formatter that would introduce unrelated code changes.

Report:

- the scope inspected;
- the number of comments or blocks removed and trimmed;
- preserved borderline comments that need human judgment;
- checks run and their result.

If no comments meet the deletion test, say so plainly and make no edits.

## Research basis

These rules follow the shared guidance that code should carry the obvious
mechanics while comments preserve information the code cannot express:

- [Google Engineering Practices: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)
- [Google Documentation Best Practices](https://google.github.io/styleguide/docguide/best_practices.html)
- [Stack Overflow: Best practices for writing code comments](https://stackoverflow.blog/2021/12/23/best-practices-for-writing-code-comments/)
- [Refactoring.Guru: Comments code smell](https://refactoring.guru/smells/comments)

The AI-specific failure mode is usually not a unique comment category. It is a
higher volume of familiar smells: line-by-line narration, generic signature
echoes, tutorial prose, and comments written for the temporary diff instead of
the maintained code.
